# FX EASY 世界经济与事件层:平衡校准记录

> 状态:实测记录。11 个校准场景,外加一次存档恢复核对。S1 于 2026-10-15 在波动缩放后重测(见第 6 节),其余场景未重跑,理由写在第 6 节。
> 证据来源:`src/test/java/com/pppopipupu/fxeasy/event/CalibrationRun.java`(临时校准程序,跑完即删)驱动真实模型类:`MarketEngine`、`WorldEconomyState`、`EconomyModel`、`MarketEventEngine`、`TradeEngine`、`FeeModel`。世界种子 `20261012`,市场时钟 24000 tick 一经济日,600 tick 一经济桶。
> 边界:这是纯逻辑模型的演算,不是服务器实测。没有测真实服务端 tick 开销、多人并发、网络包大小和真实玩家行为;只有一个种子的一次抽样,噪声数字不是分布统计。

## 3. 本次校准发现并修掉的问题

**存档恢复会把世界经济重估再应用一次。** 修复前:保存时行内 `anchor` 写的是市场进程状态(等于当前价格),恢复时 `restoreComponents` 又按 `anchor + fundamental + event` 重建价格,于是每次读档价格都会再跌一次基本面幅度。实测黄金在 -28.85% 基本面下读档再跌 25.06%。修复:

- `FxState.snapshot` 写分解锚点 `logPrice − fundamental − event`;
- `MarketEngine.restoreComponents` 同时设置进程状态与对数价值,使恢复后的价格与保存时完全相同,下一 tick 从该价格继续。

回归测试 `FxSnapshotTest#aSaveInTheMiddleOfARevaluationKeepsItsPrice` 在修复前失败、修复后通过。

## 4. 没有测到的部分

- 真实服务端开销:原定目标(<0.5 ms/tick 平均、封桶峰值 <2 ms)需要代表性服务器上的计时,本记录没有做,也不声称达标。
- 多人并发与网络:容量缩放只按玩家数模拟,没有真实多人会话、登录退出抖动或包大小统计。
- 事件满载:本记录的场景都没有让事件层同时跑满 3 个计价事件;事件层的生命周期、预算、冷却与回吐由单元测试(`MarketEventEngineTest`)覆盖,不是本校准的一部分。
- 单种子抽样:所有数字来自一个世界种子,不能当作收益分布;噪声相关的结论只说明"没有异常放大",不说明长期统计。

## 5. 币种系统重构之后

2026-10-13 的第五轮把币种做成了数据定义 (世界 `serverconfig/fxeasy-currencies.json`)、取消了"价值点"这个第三单位:现在任何金额都是某个币种的物品数,价格只是两个币种之间的汇率。这份记录里的数字全部是**相对变化** (pair 涨跌百分比、基本面百分比、保证金水平与杠杆倍数),与单位无关;每个币种的容量/供需权重也与重构前逐值相同 (16384/4096/2048/96/8 与 0.35/0.08,土块 0.08/0.02,现在写在币种定义里),所以本表仍然有效,本轮没有重跑。

## 6. 波动缩放之后

2026-10-15:市场自己的波动提高了 1.5 倍,并且变成可按世界调节。

- `MarketEngine.RESIDUAL_NOISE_SHARE` 0.35 → 0.525(噪声),`references` 的参考值同步乘 1.5,所以 regime 仍以"1 = 这颗世界的常态"读数:调高波动只是把市场整体放大,不会让平台把同一个市场判成恐慌。
- 新增 `MarketEngine.DEFAULT_VOLATILITY_SCALE` 与配置项 `market.volatility_scale`(0.1 ～ 8.0,读档时取值,不在 tick 路径上读),`FxState` 建市场时传入;世界按自己的整档方差运行,不按币种单独调。

本轮只重测了受噪声直接支配的 S1(见上),其余场景没有重跑,理由如下:

- S2 ～ S12 的结论来自基本面与压力项(`EconomyModel`、`EconomyConstants`)和费用模型(`FeeModel`),这两处本轮没有改动。
- 供给侧场景的量级(-5.65% / -24.22% / -25.85% 等)由基本面项主导,噪声项(30 日 1σ 约 1.2% ～ 4.0%)只在其上叠加几个百分点;这些数字应当理解为"同一方向、同量级",不是逐位可复现。
- regime 与交易成本的关系没有变:参考值与噪声同比例放大,S1 里整轮 regime 读数为 1.0000(见上),所以点差、掉期与保证金折扣的档位与调参前一致。

需要重跑的情况:改动 `economy/EconomyConstants`、`market/FeeModel`、事件目录,新增/调整币种定义的价格、波动、利率与容量,或者改动 `MarketEngine` 的噪声/波动常量(`RESIDUAL_NOISE_SHARE`、`DEFAULT_VOLATILITY_SCALE`)。

## 7. 做空开仓加点差之后

2026-10-16:开仓点差按方向分档,做空比做多贵一点。

- 新增 `FeeModel.SHORT_OPEN_SPREAD_MULTIPLE = 1.5` 与 `FeeModel.openHalfSpread(Side, regime, discount)`:开仓单走 `FeeModel.openFill`,卖出方向(做空)付 1.5 倍半点差;平仓单仍走 `FeeModel.fill` 的对称半点差。一次做空的点差成本因此比一次做多高 0.5 倍半点差,且只在开仓那一步收,不平仓时再收一次。`TradeEngine.open` 换成 `openFill`,`Position.closingPrice`(权益标记)、`bid`/`ask`(行情报价)与 `TradeEngine.close` 都不动,面板的费用条改读 `FxClientState.openSpreadHalf(orderSide)`。
- 折扣、regime、滑点与掉期都没动:`openHalfSpread` 是 `halfSpread` 乘一个方向倍数,计划折扣照旧作用在点差上;`openFill` 与 `fill` 抽随机数的次数与顺序完全相同(同样的 `nextChance`),所以同一颗种子下非做空场景的抽取序列逐值不变。
- 受影响的场景只有 S9(先做空再扩产):开仓价下移,实现利润相应减少。S9 记录的开仓价与当时中间价之差是 9.72e-5,按 1.5 倍计,多付的是这一次开仓点差的一半;S9 自己记录的总成本约 1.9 土块,所以增量至多 0.5 土块,相对 +1523.93 土块在 0.03% 以内,结论(方向、量级、"成本只吃掉毛利约 0.1%")不变。上面这段是按公式算出的上界,不是实测值。
- S1 ～ S8、S10 ～ S12 不受影响,理由:它们的开仓方向都是买入(`openFill` 与 `fill` 在买入方向逐值相同),平仓与强平走的是对称的 `fill`,抽取序列也没有变。
- S9 ～ S12 没有重跑:它们的驱动 `CalibrationRun` 是临时程序,跑完即删,仓库里没有;要重跑就得重写一个只覆盖 S9 的驱动(同一颗种子 20261012、同样的开仓与扩产顺序),本记录没有做。
